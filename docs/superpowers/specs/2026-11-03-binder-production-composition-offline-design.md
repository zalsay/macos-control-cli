## Observed source and invariant

`RunnerMain.start` parses `RunnerLaunchSpec`, obtains the default workspace and profile, acquires and retains its `ProfileLock` in `RunnerMain.lock`, checks background profile/spec and the connected input stream, then calls `RunnerAutomationEntry.serve(profile:spec:workspace:arguments:rawInput:)`. That extension in `RunnerPreparation.swift` first checks `NativeInputPreflight.shippingAdmissionAvailable`, currently literal `false`, adopts the channel and calls `AutomationRunnerBootstrap.serveUnavailable`. Only beyond that guard are the factory/native checks, disconnect watcher, preparation, `RunnerMain.makeAutomationService`, service lifetime and resource close. Separately, the Foundation-only `RunnerAutomationEntry.serve(profileID:channel:)` at the end of `RunnerAutomationService.swift` calls the unavailable bootstrap in both branches. It is not the full App entry.

The unavailable bootstrap uses the existing `AutomationRunnerServer`: capabilities report backend unavailable and other requests reach `backendUnavailable` subject to the server's own protocol/session validation. The `WebViewConfigurationFactory.requireExecutionPolicy`, `NativePageInput.requireShippingAdmission`, `RunnerMain.makeAutomationService`, service and owned-page checks are independent existing boundaries. Preserve their exact behavior and wire errors; never add a redundant boolean gate or change them for this stage. A static check of full App ordering is owned independently by main, not repeated here.

The 031 and 040 frozen repository providers retain pinned directories, role-specific lock handling, actual parsed spec equality, bounded repository reads and matching hashes/snapshots, profile/plan restrictions, complete `RepositoryObservation` baseline equality, deadline/cancellation checks and fail-closed release. The fixture derives a `workspace` adjacent to an executable with a `BinderProbe` suffix; its integration supplies a compiled UUID/spec and uses a byte socketpair for synchronization. These are test mechanics, not production identity, authority, a human grant, or the real application protocol. The provider explicitly takes a caller-supplied path; even a plausible signed-looking string does not prove kernel executable identity. Existing fixture lock acquisition is not the original live Runner held lock. Transport PID/nonce handshake alone is not Binder kernel authentication.

## Future real composition obligations — not implemented or authorized here

Before any production provider can exist, a future reviewed design must connect provenance and lifetime, not merely validate once:

* Kernel identity evidence must come from an OS-backed observation tied to the actual connection and owned child process, with PID-reuse and connection lifetime addressed; no caller path, nonce or fixture claim is a proof. Manager retains the real `OwnedRunnerProcess` and only cleans up its own child.
* Bind that process observation to the actual Bundle/executable and resource identity, original launch spec/argv as generated and parsed, actual workspace root, repository observations and selected profile. State explicitly which launch facts are observed versus not kernel-attested, and defend replacement/races to the level actually demonstrated. Fixture `BinderProbe` layout and compiled UUID/spec cannot provide these facts.
* The runner must retain and verify the **original already-held `RunnerMain.lock` object/handle** against the real workspace lock throughout the relevant lifetime; reacquiring a pathname in a fixture is not an equivalent proof. Repository equality includes all fields currently in `RepositoryObservation`, not just profile ID or content hash. Connection closure, lock loss, replacement, cancellation, deadline, generation change and cleanup fail closed.
* A non-forgeable, owned, generation-bound context must be carried from the original entry through preparation and `RunnerMain.makeAutomationService` into `RunnerAutomationService` and its owned page/resources, retained while operations may execute, and revalidated at relevant asynchronous boundaries and before action/commit; no check-once token, discarded witness, or fixture-backed approving factory. Context invalidation must quiesce input, cancel in-flight work, and close owned resources without affecting unrelated processes. The precise production type, isolation, cleanup order and revalidation points require subsequent design and main review; this is a requirement, not a claim the current code implements them.
* Kernel/process/repository evidence is distinct from factory/native/service admission, real GUI ownership, direct human authorization and real keyboard/mouse coexistence evidence. Existing hard-false gates stay unchanged until individually authorized and verified; Binder evidence alone cannot grant GUI access.

## Blocking protocol/ordering distinction and minimal future wiring map

The frozen staged `ControlEnvelope` sequence (`hello/proof/ack/identity/ping/finish`, plus responses) is **not** the product's `AutomationHandshakeCodec` `hello/ready` followed by `AutomationRequest` v1. They are incompatible protocols: do not wrap the existing server in staged `AuthenticatedConnection`, run two handshakes on the same fd, start two readers, prepend private frames to v1, or call the ordinary nonce/PID handshake kernel proof. `AutomationRunnerServer.serve()` owns the channel reader and itself consumes `hello` and sends `ready` before the request loop. The current App extension instead reaches `prepareBackground` and `RunnerMain.makeAutomationService` (which may create `NSApplication`) before `service.serve()` starts that read. Its startup watcher uses `poll` to detect disconnect; it does not consume or authenticate protocol frames. Thus a purported check inserted only in `server.serve()` is too late to protect backend preparation.

**Blocking prerequisite, not implemented:** before any positive production wiring, separately design and independently review a wire-compatible authentication seam, exact ownership and exclusive reader/handshake-consumption handoff. Kernel identity capture and binding must occur before any backend/GUI preparation; preserve v1 bytes and v1's default unavailable behavior. The design must specify whether and when the existing v1 hello is read/responded to and how one exclusive owner transfers an already-started channel/handshake state without a second hello or concurrent reads. If that cannot be proven without a protocol change, positive wiring remains prohibited; no private prelude or new version is authorized by this phase. The existing watcher may observe disconnect but is not an authenticated reader or a substitute for the seam. Full cancellation, EOF, timeouts, races and resource cleanup require dedicated tests and independent review.

| Future change locus | Required order, ownership and cleanup (design obligation; no current implementation) |
| --- | --- |
| `RunnerMain.start` | Retain original `RunnerMain.lock`, parsed spec, actual workspace and original channel; lend/transfer a lifetime-safe binding of **that same held lock**, not reacquire by pathname. Keep ownership until all downstream work is quiesced. |
| `RunnerAutomationEntry.serve(profile:spec:workspace:arguments:rawInput:)` | Keep current literal-false unavailable branch and factory/native guards. A separately authorized seam must authenticate/bind before `prepareBackground` or `makeAutomationService`; coordinate watcher and cancellation without consuming the channel twice. Failure, EOF or cancellation closes only owned resources and does not prepare the backend. |
| `AutomationRunnerServer.serve` / `AutomationHandshakeCodec` / `AutomationChannel` | Define a single v1 frame reader and explicit ownership transfer of any consumed hello/response state to the request loop; preserve public handshake and error semantics. Kernel/owned-child evidence is out-of-band to v1 fields, not a nonce/PID claim. No code shape is approved yet. |
| `RunnerPreparation.prepareBackground` and `RunnerMain.makeAutomationService` | Only after binding and existing independent gates, carry the same live generation-bound context and owned resources forward; revalidate on async transitions. On disconnect, cancellation or stale binding close owned preparation resources before releasing their supporting ownership. |
| `RunnerAutomationService` and `OwnedBrowserAutomationPage`/owned resources | Retain the same context while page/action work exists; enforce revalidation before relevant operations and commits. Invalidation quiesces input, cancels operations and closes owned page/service resources before releasing original lock/context. Neither one-time checking nor make-and-discard is sufficient. |
| Manager launch/`OwnedRunnerProcess` | Retain actual launched owned child and connection provenance for its lifetime; on failure terminate/observe only that owned child, not a PID scanned or supplied by a frame. No fixture observation establishes human/GUI authority. |

Split future work into separately approved, bounded units: (1) protocol/reader ownership design and adversarial v1 compatibility tests; (2) pre-preparation kernel/owned-process/original-lock binding and cancellation handoff; (3) context lifetime through preparation, service and page with invalidation/cleanup tests; (4) independently authorized real GUI/human evidence and unchanged gate assessment. None is part of Tasks 2/3 or permission to alter product source, wire version, UI or shipping gates.
