# Offline Profile binding design

Scope: fixture-only data snapshots of the actual Profile and RunnerLaunchSpec, resolved with RunnerPreparationPlan.resolve. Require explicit opt-in, ephemeral mode, background about:blank and no outbound or follow-proxy settings; readers never access profiles, secrets or credentials. Full UUID and whole Equatable values are compared. The existing authenticated connection generation owns one binding; no new identity authority or protocol field is introduced. Any mismatch, mutation, repeat binding, cancellation or late completion revokes the original connection. Recheck the generation, original deadline, cancellation and snapshot across awaits.

A data-only Profile snapshot does not prove repository freshness or locking, window ownership, or human consent. A future live boundary must collect trustworthy evidence directly from the actual Runner-owned application and window lifecycle, bind that evidence to the authenticated process generation and visible window, and require a direct human grant scoped to that exact lifecycle. Revocation, lifecycle changes, deadline and cancellation must invalidate it. Callbacks or caller-provided claims cannot create that authority. This document does not implement or approve such a provider. The default provider is unavailable and any request must deny and poison the connection. The existing synthetic GG guard is not real proof.

No GUI, application launch, system automation, credentials, permissions or live input. G1, G5, fullP1, input, shipping, liveAdapter, GUIExecutionAuthorized, manualGrant, ready and armed are all false.

## Existing paths and future evidence collection (design only)

`Sources/Safarier/RunnerMain.swift` `start` acquires and holds `ProfileLock`; `Sources/Safarier/RunnerPreparation.swift` calls `RunnerPreparationPlan.resolve`. `Sources/Safarier/Browser/BrowserSession.swift` `makeAutomationPage` calls `OwnedBrowserAutomationPage.attach`, whose `Sources/Safarier/Automation/OwnedBrowserAutomationPage.swift` `checkedObjects` validates its objects. `Sources/Safarier/Automation/RunnerAutomationService.swift` `repositoryPermission` re-reads only a Boolean: it cannot prove full configuration freshness or a repository revision/lock.

A future, separately authorized `@MainActor` collector would retain the actual session, controller, webView and window and validate their ownership chain by `===` on each check. It must not enumerate `NSApp` windows or adopt foreign windows. Its evidence must associate kernel-owned generation, full Profile UUID and configuration, repository revision and held lock, lifecycle epoch, strong object ownership, an actual foreground direct-human interaction, one-shot grant scope and deadline. UUID, window number, callback or fixture cannot themselves be authority. These are requirements for future design, not evidence available now: live GUI capture remains unavailable.

## Offline reader deadline and lifetime

The original `FrameDeadline.run` uses a structured group; on its own it cannot bound an arbitrary reader that ignores task cancellation, because group exit waits for children. The staged fixture reader is therefore mediated by a one-shot cancellation-aware continuation; the original deadline races that cooperative bridge, not the arbitrary reader directly. Cancellation or timeout closes and revokes; the registered reader task is cancelled and a late completion cannot write the snapshot. Connection gate serialization allows at most one inflight reader; after revocation no further reader can start. An uncooperative reader cannot be forcibly stopped and can retain its own captured data and one completion box until it returns (or process exit); this is not a claim of leak freedom. No reader callback conveys authority. After each pre-I/O profile await, repeat actual kernel/resource verification before I/O; after I/O recheck snapshot, generation, deadline/cancellation and kernel identity.

The bridge itself does not explicitly capture the connection, but an injected fixture reader may retain arbitrary objects, including the connection. An uncooperative reader may remain as at most one outstanding task for that closed connection; it is not restarted or reusable. This does not guarantee termination or prove absence of all leaks. EOF drain is special: the child may legitimately exit after receiving EOF, so repeat kernel verification before shutdown; after EOF use the retained `OwnedRunnerProcess` exit observation rather than requiring a live peer.

## Fixture authority boundary

Both peers bind their own matching data-only fixtures after ACK; this adds no authenticated on-wire Profile attestation. The matching fixtures do not establish real Profile or GUI binding, launch provenance, repository provenance/freshness, a held Profile lock, window ownership, or human consent. The tests and direct dependency/symbol audit are offline evidence only and do not establish transitive GUI absence or runtime acceptance.
