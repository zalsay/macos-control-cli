# Offline repository and original-lock binding design

## Scope and trust boundary

This design covers the approved 2026-11-03 continuation as a **controlled, private, offline CLI fixture**, staged under `.build/automation-binder-repository-20261103/worker`. It is not integrated into product Sources/Tests/scripts/Package, not a real Manager/Runner, and not production or GUI authorization. The only code review for this work is the main Agent's `main-code-review.json`; it accepts the offline implementation within that scope and records no unresolved code finding in the approved scope. Execution discipline is a separate, non-clean result; see the verification document.

`RepositoryBindingProvider.make(executablePath:role:expectedSpec:actualArgs:environment:)` requires the **caller to supply an already kernel-verified executable path**. The provider does not authenticate that argument itself and is not a standalone production authority. In the fixture, the previously verified bridge path determines the fixture parent and fixed `workspace` child; neither wire data nor arbitrary environment selects a repository. Root, workspace and locks directory objects are pinned with no-follow descriptors and lstat/fstat device/inode, EUID and exact 0700 checks, and rechecked. Before the original `ProfileLock.acquire`, the exact precreated lock is checked as regular, EUID-owned, 0600 and single-link; its instance and the directories are checked again after acquisition.

The endpoint actor privately retains the original ProfileLock object and serializes observation and release. Its staged copy adds only an internal read-only check comparing its open descriptor's fstat to the no-follow path's inode/device, type, owner, link count and mode; no FD escapes, no lock reacquisition is used as proof, and PID text/isHeld is not authority. Controller does not claim to hold or inspect the child's descriptor. Original acquire/release and owner-plus-fresh-metadata cleanup are preserved; unlinking and recreating a lock path can permit another lock on a different inode, so detected path loss invalidates the provider rather than changing original flock semantics.

## Repository and connection observation

`RepositoryObservation` carries complete raw bytes, records, profile/spec and an exact file-instance observation; equality is not limited to the selected Profile tuple. The fixture uses the original `bi_snapshot` implementation through an internal per-call size limit, the original C file comparison, SHA-256 of bounded raw bytes, `JSONDocumentStore.decode`, and original `ProfileRepository.all()`. A staged internal bounded load path protects the repository read while leaving the original default store API behavior intact. Pre/post observations, raw digest, full decoded record comparison, unique UUID selection and the original preparation plan must agree. Missing, insecure, symlink/hardlink, unsupported, oversized or changed inputs fail closed. JSON document `version` is a format version, **not a global revision or transaction sequence**. The original 64 MiB C limit remains for the old snapshot/static/self/peer paths; the fixture's repository wrapper is bounded to 1 MiB.

The existing authenticated connection owns the single private generation, pending state and operation gate. The concrete provider is bound to that generation; pre/post-await reads compare the entire observation. Cancellation, late completion, stale generation, rebind or a detected change revokes the connection; the existing one-shot bridge prevents an uncooperative reader from committing later. The caller converts the current `FrameDeadline.remaining()` once to one C monotonic deadline for each complete provider read, then rechecks the original deadline, cancellation and generation. The existing per-frame ceiling is 3 seconds and connection lifetime ceiling is 45 seconds. These checks cannot interrupt a blocking OS call and do not establish an exhaustive memory or thread-safety proof.

The controller retains its original spawn context and generates child argv using `RunnerLaunchSpec.arguments()`; the actual child uses the original `RunnerLaunchSpec.parse` and compares the result to the local expected spec. No Profile/spec/root comes from the wire, and this is **not kernel argv attestation**. Existing Control/Transport, peer/Bundle checks and owned-child cleanup remain the authority; no second identity or locking machine is introduced.

## Fixture evidence and limits

Signed CLI bundles and their repository/lock workspaces are separately precreated; workspaces are outside signed Bundles. In the repo-bound test image only, a separate byte socketpair provides ACK/binding/mutation scheduling observations. It is **fixture-only synchronization**, not a new real control transport, peer authentication or human/GUI grant. The legacy normal image does not contain those fixture hooks. Direct dependency/symbol audits cover the inspected binaries, not all transitive or runtime behavior.

Pre/post observations are not an atomic cross-file transaction and do not prove resistance to a malicious same-UID process, delegated/transferred FDs, or races between checks. No real profile repository, credentials, installed candidate application, GUI, TCC, input coexistence or human grant was accepted by this fixture. GUI provider remains hard unavailable; `fullP1`, `G1`, `G5`, `input`, `shipping`, `liveAdapter`, `GUIExecutionAuthorized`, `manualGrant`, `ready` and `armed` remain false. Real GUI acceptance remains unverified.
