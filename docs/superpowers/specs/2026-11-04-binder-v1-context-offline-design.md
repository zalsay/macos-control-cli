## Authority, lifetime, and synchronization

1. Fixture runner creates the channel and inspector from the same inherited endpoint, then a single bridge, captures real self/resources and actual parent metadata, validates actual peer against parent, creates **one** runner provider with the verified executable and performs its initial `read`. The initial observation pins repository version; the acquired provider lock is never released/reacquired while active. The inspector must remain retained and refer to the same endpoint; no reading on it.
2. Create the context *inside the staged server's ownership boundary* with a strong reference to that exact `AutomationChannel` and server-associated `seamID`/phase. The server must validate actual object identity (`===`) and its own phase/one-shot handoff ownership when installing/using it; the context is not exportable or constructible from an arbitrary UUID, public token or wire field. Choose a narrow internal staged-only method/signature after main adjudication. No second authority store or duplicate provider. A new server/channel requires a new context and initial baseline, never a transplanted context.
3. Serialize mutable bridge peer baseline, provider/read/release and state transitions in a single context isolation domain. In particular, do not race `matchesHeldFile` with `release`, or concurrently call mutable `checkPeer`. Avoid holding a blocking lock across `await`: capture generation/state, perform permitted work, then re-enter isolation and recheck generation and terminal state before committing. If implementation cannot both serialize a potentially blocking OS call and guarantee bounded teardown, it must explicitly report that limitation; cancellation cannot force that call to return.
4. Lifecycle is `constructing -> bound -> handshake -> ready-sent -> preparing -> serving -> closed`; phase transitions must be checked against actual staged server phase/handoff, not merely a parallel enum. Any cancellation, peer EOF/disconnect, timeout, identity/repository/lock mismatch, protocol failure or explicit close causes irreversible `closed`; no later completion can revive it. Teardown closes owned channel, cancels tasks/timers and pending preparation, rejects queued/late completions and releases provider/inspector exactly once after their last safe use. `OwnedRunnerProcess` cleanup is controller-only and bounded; no PID from wire, process scan, or identity alone authorizes kill. Record an unconfirmed cleanup separately.

## Checkpoint contract (requirements, not a verification claim)

Pre-hello has the explicit adjudicated exception: validate self/resources/actual parent/provider/lock, but do not assert peer socket last-use. After the original hello, establish peer before ready. At every applicable full checkpoint, fail closed on cancellation, deadline, channel/generation/phase/closed mismatch or disconnect; perform actual bridge self/resources/parent/peer/parent checks and the *same provider* `read`, including runner lock and baseline, then repeat state, generation, cancellation and deadline checks. Never turn these into `() -> Bool` caller claims. A fresh operation deadline must be bounded by the existing lifetime; derive the provider's absolute C monotonic deadline from the same remaining budget (do not renew lifetime). Actual C calls and repository filesystem/decode are synchronous and may return late; check after each call before any next commit.

| Boundary | Required validation / observable behavior |
|---|---|
| Handshake read/ready write | Before hello, use the adjudicated pre-hello checks without a peer claim. After the original hello, pin the actual peer before ready; before ready write and again after return check complete context and original handoff/phase. If precheck fails no ready; if postcheck fails close and never hand off. Bytes already sent cannot be recalled. |
| Preparation | Before dispatch, after each awaited operation and before/after completion admission check context and one-shot handoff. A late completion cannot commit or retain live authority; isolate the duplicate inspector lifetime from potentially noncooperative work. |
| Request receive/decode/admission | Check before receive, after receive await, before decode result admission and before scheduling each handler. Malformed diagnostic is also an outbound write subject to generation/context checks; do not emit it after validation failure. Keep original framing and limits. |
| Handler | Check before invoking unavailable-only handler, after its await and before publishing outcome. No side-effecting or user-provided arbitrary handler is authorized by this fixture. Cancellation cannot undo a handler's prior effects; the permitted handler must be side-effect-free. |
| Outcome/queued write | Requirement: revalidate before enqueue, at the actual serial channel writeQueue dequeue/system-write admission, and after write completion before internal success bookkeeping. **Attempt 014 has server-side presend and postsend checks, but no full identity/repository revalidation inside the channel writeQueue at actual dequeue/system write.** A queued write can wait after the presend check. This is an unimplemented production blocker, not an atomicity guarantee. |
| Close/cancel | Monotonic close immediately prevents new admission/commit; cancellation/timeout close channel and mark terminal before releasing owned resources when safe. Test repeated/overlapping close and late return. |

Revalidation is point-in-time detection, **not an atomic transaction** with the OS peer, repository, network write, or handler: peer may exit or descriptor be delegated after last observation, filesystem/identity can change between checks and actual use, and a partial or completed write may already be visible before a failure is detected. No claim of peer liveness at last byte, continuous identity, atomic cross-file snapshot, hostile same-UID resistance, or ability to forcibly cancel a noncooperative callback. Cancellation must fence future commits, not promise interruption or reversal. Serialize the check/write admission and sticky close as narrowly as practical, without claiming OS-level atomicity.

## Actual product path and fixture distinction

`Sources/Safarier/RunnerMain.swift` acquires its existing `ProfileLock` before entering `RunnerAutomationEntry.serve`; `Sources/Safarier/Automation/RunnerAutomationService.swift` routes the entry to `AutomationRunnerBootstrap.serveUnavailable`, including when shipping admission is unavailable, and `Sources/SafarierCore/AutomationRunnerBootstrap.swift` constructs the server with the unavailable handler. This is a reference path only: the **fixture** original lock in this proposal is acquired and retained by `makeFixture` in the fixture runner, not the separate product `RunnerMain` lock; nothing here wires or transfers product ownership.

`RepositoryBindingProvider` is an actor: external `read` and `release` are asynchronous actor crossings. Its internal read is synchronous and serial on that actor; the server must recheck its own generation/closed state after each crossing. Actor serialization alone does not make server-state checks and OS writes atomic, nor ensure a blocked read can be interrupted. The fixture factory derives root from the verified `.../<fixture-root>/<name>.app/Contents/MacOS/BinderProbe`, checks parsed actual arguments against `expectedSpec`, pins `<fixture-root>/workspace` and `locks`, and requires an existing safe lock file before acquiring it. `executablePath` is trusted by the factory only because the caller must first verify it; the factory itself does not authenticate it.
