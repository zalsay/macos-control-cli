# DSH startup plugin compatibility warning

The user reported a brief error during DSH restart. The installed controlled runtime was `0.2.2-rc.2`; the persistent web profile still declared `@deepseek-ai/dsh-experimental-plugin-market-bundle` `0.2.2-rc.1`. An isolated startup using copies of the profile configuration reproduced a warning that `@deepseek-ai/dsh-plugin-market@0.2.2-rc.1` required rc.1 runtime services and was therefore disabled by DSH. The server subsequently started, explaining how a startup warning can disappear when the App switches from startup output to the web console. This is the captured warning; the user did not retain the original brief message.

## Correction and validation

- The npm registry publishes the market bundle `0.2.2-rc.2`, with `dsh-plugin-market` and `dsh-client-ui-plugin-market` dependencies pinned to the same rc.2 version.
- A complete isolated profile copy was updated through the existing `dsh plugin --profile web add --save-exact …@0.2.2-rc.2` command. Startup ran for 18 seconds, announced its loopback URL, produced no matching warning/error lines and exited zero after SIGTERM. Earlier temporary copies under a different directory depth encountered pnpm store and relative local-link relocation problems; using the same filesystem and directory depth as the actual profile resolved the fixture issues. These were isolated-copy errors, not additional observed live startup errors.
- The actual web profile was backed up, then updated through that same official CLI. Only the selected direct dependency version changed. `cordis.patch.yml`, `cordis.yml` and `pnpm-workspace.yaml` remained byte-identical. Other direct plugins retained their installed versions: `dsh-acp-agents` 0.4.8, `dsh-provider-proxy` 1.1.1 and `dshmarket` 1.73.17. No compatibility exemption was added.
- The existing native App menu's **重启服务** action was invoked. DSH PID changed from 64518 to 66144, owned by the same Manager PID 58512. The two browser PIDs, 58538 and 58541, were preserved. The new DSH process listened only on loopback and returned the expected unauthenticated HTTP 401. This listener check alone does not prove authenticated UI behavior.
- A boot-free composition of the actual updated profile exited zero, produced empty stderr and contained the plugin-market tools entry. Native startup text capture saw the startup labels but did not capture complete stdout; it is not used as proof that every live startup message was absent.

No App source or runtime image changed, and no full regression was run. The main agent checked the profile manifest/config changes, installed versions, process replacement and preservation of unrelated browser processes. The controlled runtime's original version compatibility checks remain in force.

Private evidence and rollback backup: `.build/dsh-restart-20261116/`. `isolated-summary.json` preserves the reproduced warning, `candidate-summary.json` records the corrected startup, `actual-plugin-update.json` records the package/config review, and `final-review.json` ties together the actual restart and checks. The original web profile remains in `actual-profile-backup/`; raw configuration and startup logs can contain secrets and are restricted to the local user. Isolated profile copies were disposed after verification. No commit or push was performed.
